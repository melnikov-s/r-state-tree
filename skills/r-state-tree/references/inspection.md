# Live inspection and agent control

Read the complete [inspection setup and security guide](../../../docs/inspection.md) before configuring this feature. In an installed application, it is at `node_modules/r-state-tree/docs/inspection.md`. If this skill was copied separately, locate that guide in the installed package rather than reconstructing the transport from source.

## Setup checklist

1. Confirm the installed version exports `r-state-tree/devtools` and `r-state-tree/devtools/vite`. Do not assume older releases support them.
2. Install the optional tooling peers `ws` and `@modelcontextprotocol/sdk` as app development dependencies, using the versions in the guide.
3. Add `rStateTreeInspector()` to the app's Vite plugins, with loopback-only serving. For Electron, use the renderer's Vite configuration, not the main process.
4. In renderer startup, behind `import.meta.hot`, create an inspector, explicitly register existing Store/Model roots, and call `connectViteInspector` with the virtual module token. Add the virtual module type reference. The panel is optional; register HMR cleanup for all resources. Do not eagerly initialize children to register them.
   Panel placement: `mountInspectorPanel(inspector, { fullscreen: true })` starts viewport fullscreen; `{ container, layout: 'embedded' }` fills an app-supplied pane (give it a height). Default is a collapsed floating panel. The toolbar toggles fullscreen and Escape restores layout without recreating the UI. This is same-renderer UI, not OS fullscreen or a separate Electron window; cross-renderer visual viewing needs an adapter not currently supplied.
5. Keep `controls` disabled unless the user wants field writes and method calls. When enabled, both panel and MCP gain privileged app control, including possible real external effects. No separate action registry is required.
6. Gitignore `.r-state-tree-inspector.json` and its temporary files. Vite generates this owner-only file with the current relay address and secret; it contains no app state. Never paste its contents into agent instructions.
7. Configure the user's actual MCP host to launch the installed `r-state-tree-inspector` executable (or `node` with the installed `dist/devtools-mcp.cjs` path). Set `RST_INSPECTOR_RELAY_FILE` to the absolute generated-file path under the app's Vite root. Host config locations/formats differ: identify the host rather than inventing a universal config file.
8. Start the app and leave its renderer/window open. Verify `rst_list_tabs`, `rst_list_roots`, and `rst_inspect`. With multiple windows, use the returned `tabId` explicitly. Read live state after a harmless app interaction to verify the full connection. Do not claim success based only on adding configuration.

## Using the tools

Discover roots and methods before calling them; names and IDs are app-specific. `rst_inspect` can list methods in read-only mode; writable capabilities, `rst_set_field`, and `rst_call_method` require controls opt-in. Inputs are JSON, not executable expressions; framework/native prototype methods are excluded. Direct redacted paths are inaccessible, but allowed application code is not sandboxed.

In Vite development, method entries can also include named `parameters`, source type labels, optional/rest flags, input kinds/literal choices, and `returnType`. These come from a dev-only source transform, not runtime type checking. Imported/complex aliases may remain unknown, and missing metadata does not mean a method takes no arguments. Select the owning subtree with `depth: 1` and a larger `maxEntries` when signatures are omitted by the budget; state values take priority over signature metadata. Defaults are withheld and should be omitted from trailing arguments rather than guessed. The panel uses the same metadata for parameter inputs and shows a persistent tree with inline scalar edits. Its Props section directly lists values and callable props. Discover callbacks by inspecting the Store's `['props']` path, then invoke through `rst_call_method` with that same path and the callback's property name; do not assume callbacks are Store methods. Fresh object-literal callbacks preserve development-time signatures across props copying/aliases; referenced or bound functions may lack metadata.

Use `rst_inspect({ evaluateComputeds: false, ... })` for ownership/structure discovery without evaluating ordinary computed getters or Store keys. The panel's Diagram uses that mode, with separate Stores/Models tabs, selectable cards, ownership branches, and optional Store Context availability routes. Each diagram keeps its own selection and viewport; cross-kind roots/references are not mixed. The details overview groups props, available Context, state, computeds, children, and methods.

Store inspection can include `contexts` metadata from dev-only source declarations and real ownership ancestry. `providerId` identifies the nearest known provider; `declared` is inferred source use, not an actual-read trace. Context listing never evaluates providers. Use `rst_inspect_context` with the returned `contextId` and the same selected root/path for an explicit bounded read; this can execute app providers and does not grant control over returned services. Defaults used only through helpers may be undiscoverable. Redact Context with `['$context', contextName]` under the selected path, and check the full guide for inherited provider policy.

For automatic development activity, enable `createInspector({ activity: true })` behind `import.meta.hot`, register roots, and dispose the inspector during HMR teardown. This records calls through observable action wrappers and successful mutations on retained registered objects, grouped by synchronous public/action batches. It is off by default and rejected in production; without roots/disposal no hooks remain subscribed. Recording has overhead: never recommend it for production. No method/repository wrappers are needed. `activity: { maxEntries: 200, redactValues: path => ... }` can retain write events while withholding document text from history. Ordinary redaction excludes fields before capture. MCP `rst_list_operations` returns automatic records alongside optional labels; the panel Operations view shows the same batches. Calls omit arguments/results/errors; writes use bounded shallow summaries, not snapshots. Async continuation writes have no invented parent-call attribution. Discovery/history/output are bounded, and raw-source/non-observable writes and objects reached only through getters/Context are not a complete trace; heed `activity.discoveryTruncated` and `truncated`. See the complete guide for collection/path limits. Clearing is not cancellation or rollback; unregistering clears automatic history.

If the app also explicitly attaches `createOperationTimeline` through `createInspector({ operations })`, `rst_list_operations({tabId?})` lists bounded command/async-operation records. Use it to correlate pending/failed work with live state, not as a complete reactive-change trace. Static labels and bounded error summaries are recorded, never arguments/results; messages can still be sensitive, so use synthetic `$operations` redaction. `abortRequested` does not prove cancellation/rollback; `unobserved` is not failure or completion. Do not replay/retry operations from the log. The panel Operations view uses manual Refresh; Clear requires controls and does not cancel running work.

Initialize lazy children explicitly when needed; normal computed reads can also initialize them indirectly. Do not assume inspection is side-effect-free. Never automatically retry a write or method call after timeout, cancellation, or lost replies: it may already have run. Inspect state first. Explain that Electron main-process state is not exposed by the renderer bridge.
